# 执行契约（S2 唯一决策源）

模型结合本次原文、历史授权和已有材料理解语义。其他阶段只引用本契约，不再按触发词重新决定范围、保存或确认。

## 先确定交付

- target：S3a 概念 / S3b 故事 / S3c 剧本 / save_only。只运行到用户要求的终点；必要的格式验证不扩展创作交付。分镜、资产计划、Prompt、检查与表演测试属于 film-director skill：记录为越界项并指认交接材料，不在本 skill 内交付。
- entry 与材料：已有故事可进 S3c；局部改写直接进入该稿层级。只补影响本次工作的缺口，辅助表缺失不等于材料未成熟。
- excluded：用户明确不做的阶段。计划与终点不能越过排除项；请求本身冲突时，先交付不依赖冲突的部分，只问必要问题。
- units：scenes（叙事范围）记录于本 skill；shots（镜头限制）与 clips（生成预算）属于生产层，不从场数推导，也不在本 skill 裁决。一个场景不意味着授权写分镜或 Prompt。

## 自主、确认、保存

- autonomy：guided / autonomous。“一次跑完／不用问我”表示自主完成指定目标；不自动确认或保存。“写故事看看”仍只交故事；未指定剧本时不自动补到 S3c。
- 硬锁是用户要求保留的具体内容；当前采用稿是后续工作的版本；探索稿是尚未采用的尝试。采用不等于永远不许修改。修改请求按 §修改请求 拆成范围、改法、采用三个独立判断，不把一句批评当成三项都已授权。
- save：yes / no / unspecified。本次明确不保存优先；否则本次要求优先于已有约定；均未约定时不落盘。历史 save_policy 可为 never / on_request / after_confirmation / always。确认后自动保存仅在该约定已成立时执行，不因“这个好”临时建立约定。
- confirmation：仅记录用户对本次对应成果的确认及来源。模型推荐、自主选择、脚本通过不是确认；旧稿确认不自动确认新稿，保存草稿不改变确认状态。
- 已有保存约定持续有效，无需每阶段重问。对话探索不创建目录；明确保存候选可在选定前落盘为候选稿，不冒充定稿。

## 修改请求：范围、改法、采用是三件事

用户对已有稿的每一句话——批评、要求、认可——都要分开回答三个问题。三个答案彼此独立，一句话通常只回答其中一两个，其余按下面的默认值处理，不猜测。

**范围（scope）**：哪一段允许动。用户批评指向的部分及其直接牵动的上下文即为范围，不必再问；其余硬锁保留。范围不因"这场不好"扩到整集、整季或依赖文档。

**改法（method）**：怎么改。
- *given*：用户给了具体改法（"把这句删掉""换成不碰的对视""压到 30 秒""名字改成 X"），或改法唯一 / 只涉措辞（错字、赘句、称呼、口误）。→ 直接改，交付改动清单 + 整段全文。
- *open*：用户只指出问题（"太强了""太假""没意思""慢""调整一下"），没有说要改成什么。→ 先判断：这个问题有几种真实不同的解法？解法之间会不会改变人物、关系走向或后续依赖？
  - 不止一种且会改变作品 → 交付 **改法选项**：两到三种，每种一两句写清改什么、这场因此变成什么、影响后面什么；可以推荐一种并说理由；**不改稿**。用户点选后才进入修订，此时改法转为 given。
  - 只有一种合理解法，或差别只在措辞 → 直接改，并用一行说明选了哪种、为什么。
- autonomy 为 autonomous（"你定""直接改""不用问我"）时，open 也直接改：自主选一种，交付时说明另一种为何没选。
- 判断依据是解法空间，不是触发词："调整一下"可以是 open 也可以是 given，看它后面有没有跟着改成什么。

**采用（adoption）**：改稿算不算数。
- 模型写出的任何改稿默认是 *exploratory*（探索稿），即使按保存约定已经落盘。落盘是保存动作，不是采用；采用是用户对这份改稿说"就这样 / 用这个 / 同步"或直接在它上面继续工作。
- 探索稿只写在它自己的位置：用户给定改法的定点修改直接改在该稿上（保存项目先按 `creative-loop.md` §三 存上一版快照）；模型自选改法（open + autonomous）的改稿进 drafts 或标为探索稿，当前采用稿不动。**未采用前都不更新依赖文档**：故事正文、分集框架、`ip.md` 正典、速览表、方法文档一律不同步；受影响处列为待复核，写在交付说明里。
- 用户采用后，按 `story-context.md` §4 只记录变化量并同步实际依赖；采用仍不等于确认（confirmation 另判）。
- 用户明确要求"改完直接同步到故事和框架"时，同步属于本次范围，但交付里仍说明同步了哪几处。

结构化记录里对应 `request.method`（given / open / unspecified）与 `request.adoption`（exploratory / adopted）；`route_check.py` 会拒绝"未确认却标为 adopted"和"open + guided 却计划直接重写"。

## 何时停

用户要选方向且选择会改变作品时，交付候选后停；改法为 open 且解法不止一种时，交付改法选项后停（见 §修改请求）；授权推荐后继续时可采用暂定方向推进。缺不可替代材料时交付已完成部分与缺口。到达目标即交付，不按 S3a/S3b/S3c 自动增加审批；明确采用停靠协作时按约定停。进入生产的后续决策由 film-director 承接。

## 结构化自检

复杂请求形成结构化记录，简单请求只需一行判断；不要求用户填 JSON。格式见 `templates/execution-record.json`：原始 source；request 的 target、entry、excluded、autonomy、save、units，修改请求另有 method 与 adoption；相关 history；本次 confirmation；hard_locks；planned_stages。未知值留 unspecified，不猜测授权。确认来源不能伪造。

`python3 scripts/route_check.py --record route.json` 只校验判断的结构、保存继承、计划边界，以及修改请求的改法 / 采用是否与自主度、确认一致，不判断自然语言理解正确性。旧自由文本 CLI 返回“需要语义理解”及退出码 2，不再猜意图。无保存任务可用临时文件检查；实际语义通过任务轨迹与用户指令对照验证。
