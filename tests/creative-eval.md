# 创作验证：实际文本优先

程序验证数据、文件和执行范围，不能证明台词好听、情绪真实或电影会成功。

## 日常维护走查

按此次改动选真实需求，先保留输入，再写输出，记录可定位的收益、缺陷与修订。硬锁、语言、范围、已知事实与行为因果分别核。作者自检明确标为非盲，不给自己打分来证明升级。2.0.0 当前实例见 `acceptance-2.0.0/cases.md`、`responses.md` 和 `review.md`。

不要把验收故事、原句、道具变成新任务的答案库。情绪原始参考可以根据用户要求复用，它与剧情样例不同。

## 需要比较版本时

这是可选评测，不是创作或安装前提。用有来源及独立哈希的本地版本快照，不依赖 GitHub 标签、冻结版本或其他技能。可用 `scripts/baseline_snapshot.py` 保存和验证快照；哈希证明完整性，不证明来源声明。

在隔离会话中以相同输入、模型与近似预算生成旧/新版输出，保留原始产物。不能在同一维护者上下文先写“旧版”再写“新版”当独立对照。

使用 `scripts/blind_eval.py` 随机化匿名顺序，记录有具体句子或行为证据的偏好；允许平局和两者都不好。是否由用户或独立评审完成按任务约定，不自动启动子代理。评审未完成时不能报告胜率。

覆盖与改动相关的难题：同题实质不同方向、无冲突关系、持续强情绪、混合情绪、长对白、信息时序、短片承载、长程后果、局部锁定、原文保真、缺失事实与语言范围。不要把字数、候选数或导演引用数当质量代理指标。

长上下文压力、真人围读和生成视频需要各自的实际输入与结果；短场景走查不替代这些验证。
